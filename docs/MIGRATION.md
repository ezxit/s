# Supabase 迁移、完整备份与旧链接接续

更换 URL / 公开 API Key 只会改变浏览器连接的位置。要在原项目停用后继续使用，需要先复制记录和附件，再更新网站的共享后端配置。所有步骤均保留源项目的数据。

## 在原项目到期之前迁移

1. 新建目标 Supabase 项目，在它的 SQL Editor 完整运行仓库根目录的 `migration.sql`。这个步骤创建数据表、检索/回收站接口和 `files` 存储桶。网页支持单个 200 MiB 文件；超过 32 MiB 自动分片存储，因此也适配免费套餐的 50 MB 单对象限制。
2. 在网站的设置中填写目标 URL 和公开 anon / publishable Key，执行迁移。迁移包含所有命名空间、回收站、图片原文件、缩略图、附件及待清理的旧附件，并保留每条记录的 UUID 和创建时间。迁移期间暂停编辑源项目；后台若仍在变化，页面会提示本轮快照需要重新处理。
3. 等待逐附件和逐记录校验成功。中断后使用同一个浏览器、同一源和目标再次执行；浏览器 IndexedDB 中保存了迁移进度及传输断点。保留浏览器站点数据直到完成。目标已有同 ID 但不属于本次迁移的记录时会停止，保护目标内容。
4. 下载生成的 `backend-config.json`，替换网站仓库根目录同名文件并重新部署。**数据复制成功与共享配置发布是两个步骤。** 配置文件包含公开 API Key，不应填入 secret / service-role Key。
5. 在无站点本地配置的浏览器中打开一个迁移前的分享链接，检查文本、长截图原图与文件下载。确认后再处理旧 Supabase 项目。

迁移断点绑定于本轮源数据快照。源数据在迁移或重试期间发生修改时，系统会保留已复制的目标数据并阻止覆盖；此时保留原连接，暂停源端编辑，选择另一个空目标重新执行。不要把“源数据已变化”后的重试理解为会自动合并两端修改。

如源项目已停用，但 Supabase 仍允许恢复，先恢复项目再迁移。源项目数据已删除且没有完整备份时，单独更换连接地址不会重新生成旧数据。

## 为什么旧分享链接仍能使用

网站每次启动都会用 `cache: no-store` 读取根目录的 `backend-config.json`。例如：

```json
{
  "version": 1,
  "default": "main",
  "routes": {
    "main": {
      "url": "https://NEW_PROJECT.supabase.co",
      "key": "PUBLIC_ANON_OR_PUBLISHABLE_KEY"
    }
  }
}
```

既有 `?s=记录ID` 使用 `main`。新分享链接同时记录 `store` 路由名；把该路由指向迁移后的项目，所有设备就会查询同一新位置。迁移生成的配置会保留并更新所有指向源项目的路由别名。不要删除已经分享出去的路由，也不要更改记录 ID。

尚未发布的自定义连接可通过链接片段 `#backend=...` 携带公开连接信息，供新设备访问。已发布的同名路由优先于链接片段，因此未来仍可把旧链接迁移到另一个项目。片段并非密码保护；本项目内容与公开 Key 的访问权限遵循 `migration.sql` 中的公共访问模型。新连接若只保存到单个浏览器，页面会明确显示仍需发布共享配置。

共享配置网络读取异常时会退回该浏览器的最近已知配置，并提示刷新失败。完成切换验证时请确保网站和配置文件在线；先验证一个全新浏览器，避免本地连接覆盖掩盖配置遗漏。

## 完整备份与恢复

设置中的完整备份会生成单个 `.slbackup` 文件，包含清单和文件二进制，不依赖原 Storage URL。旧版 Base64 图片也会转为备份内二进制；它们已经丢失的原图像素不会因迁移恢复。新上传的图片保留原始文件字节。

桌面 Chrome / Edge 支持选择磁盘目标后逐段写入，适合大量 200 MiB 附件。其他浏览器使用内存 Blob 回退，整份备份上限 512 MiB；超出时请使用支持直接保存到磁盘的桌面浏览器。任一源附件读取失败都会中止完整备份，避免生成宣称完整却缺失文件的备份。处于永久清理中的回收站记录，请先在源项目完成清理再备份或迁移。

恢复时选择备份文件和已初始化的目标项目。浏览器先验证整个档案，再开始写入；每块附件数据都有 SHA-256 校验，记录清单也有校验。导入后再次读取目标文件与记录验证。该校验用于发现意外损坏，并不代表档案经过签名；仅恢复可信来源的备份。

恢复整份档案时，解析器保留磁盘文件的 Blob 切片引用，校验每次只读取 4 MiB；不把整份多 GB 档案转成一个内存数组。上传和目标读回校验按文件依次进行，单个文件仍可能需要至多 200 MiB 的 Blob 缓存。低内存设备建议在桌面浏览器执行。512 MiB 限制针对不支持直接磁盘写入的导出回退方式，不是导入档案的总大小限制。

建议在到期前保留一份本地完整备份，迁移完成后再备份新项目。自动草稿只用于恢复尚未提交的输入，不代替服务器备份。页面关闭后不会在后台继续迁移；再次打开页面、重新选择相同备份并执行可使用本地进度续传。导入不会自动删除源数据，失败时已上传到目标但尚未建立记录的对象会保留给同次重试；在彻底放弃迁移时，可在目标 Storage 中按 `migration/` 前缀检查这些对象。

## 免费套餐上的 200 MB 文件

本应用标注的 200 MB 按 200 MiB（209715200 字节）校验。超过 32 MiB 的原图和附件会拆成多个不超过 32 MiB 的存储对象，每个对象继续用 6 MiB TUS 分块传输。一个 200 MiB 文件对应 7 个对象；网页中始终显示为一份文件。

下载时逐片校验大小和 SHA-256，然后按顺序合并。桌面 Chrome / Edge 可直接写入选定磁盘文件；其他浏览器合并为 Blob 再下载，保留原始名称，期间页面要保持打开。页面显示进度，支持取消与失败重试。普通小文件仍由浏览器原生下载管理器处理。

备份记录的是完整原文件，恢复或迁移时自动按当前规则分片。回收站、彻底删除与清理重试会处理每个实际分片；保留给其他内容引用的分片不会被提前删除。免费套餐的项目总存储量、流量及服务有效期仍由 Supabase 管理，分片处理的是单对象大小限制。

## 备份格式与接口

`js/portability.js` 提供 `window.ShortlinkPortability`：

- `resolve({url,key})`：读取共享配置，解析分享路由和本地连接，返回 `{url,key,route,published,registry,registryWarning}`。
- `shareUrl(id, connection)` / `navigationUrl(params, connection)`：保留当前后端路由。
- `validateTarget(connection, {signal})`：验证目标具有新版 schema 能力。
- `exportBackup(connection, options)`：导出完整档案；`saveAs:false` 用于测试或调用方接收返回的 `blob`。
- `importBackup(file, target, options)` / `migrate(source, target, options)`：返回 `{rows,assets,bytes,verified,configPending,registry,checkpointId}`；在线迁移还返回 `sourceChanged`。
- `routeRegistry(target, source)` / `downloadRegistry(registry)`：生成和保存待发布配置。

可选参数包含 `signal`、`onProgress({phase,done,total,message})`，以及 `upload(file,{key,config,signal,onProgress,onCheckpoint,checkpoint})` 注入。默认使用 `ShortlinkTransfers.upload`，迁移传输具备与普通附件一致的分块续传能力。备份恢复还可传入当前网站的 `registry`，以便生成配置时保留其他路由。

档案头为 UTF-8 `SHORTLINK-BACKUP-1\n`。随后每段为 1 字节类型、4 字节大端无符号长度、相应 payload：类型 1 是 JSON 清单，2 是附件元数据，3 是至多 4 MiB 二进制，4 是附件长度与各块 SHA-256，5 是档案结束计数与清单校验。解析器严格验证顺序、长度、结束标记、重复 ID、附件引用和校验值；不支持压缩，避免解压膨胀和整份档案 Base64 的额外内存占用。
